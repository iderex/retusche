# 0003. The API: a job is created and collected, progress is polled, the path carries the version

Editing is asynchronous. A request creates a job and answers with an identifier;
the result is collected in a second call. A caller learns how far the work has
got by asking, on a route it may ask repeatedly and cheaply. The surface is
mounted under `/api/v1`, the major number is the whole of the promise, and what
may change while that number stands still is written out below.

This record fixes the shape. It adds no endpoint: those are #47, #48 and #49,
and the framework that serves them is chosen there against the standpoint like
any other means. `src/retusche/api/` holds the version, the refusal shape and
the generator that turns both into `docs/api/openapi.json`, which is where an
integration reads this decision rather than here.

## What the choice is between

Three questions, and only the first is really decided by what has already
landed.

**Synchronous or asynchronous editing.** A synchronous call is the smallest
thing an integration can write: one request, one response, one image. An
asynchronous one costs every client a two-step flow and a state to keep between
the steps, even for an edit that would have taken two seconds.

**Polling or a stream.** A poll is a route like any other, authorised per job
and rate limited with the same lever as everything else. A stream, whether
server-sent events or a socket, delivers a step boundary the moment it happens
and costs a long-lived connection per watching client, a second authorisation
story and a second thing to test.

**What a version number promises.** A version in the path is a string a caller
pins and a route the server keeps serving. A version in a header is invisible in
a log and in a browser address bar. No version at all is the position that the
surface never breaks, which is a promise nobody keeps.

## Why asynchronous

The queue decided this before the API existed, and the decision is visible in
what landed. `JobDescription` is a separate type from `EditRequest`, and its
docstring says what the separation is for:

    git show origin/main:src/retusche_contracts/engine.py | sed -n '/class JobDescription/,/steps: int/p'
    class JobDescription:
        """Enough of a job to estimate its cost, without carrying its pixels.

        The queue holds one of these per waiting job. Carrying the image bytes here
        would mean the whole backlog sits in the orchestration process's memory to
        answer a question about the device's.
        """

A synchronous edit cannot be served out of that arrangement. The bytes would
have to be held somewhere for the whole wait, and admission control is what
makes the wait long: one job runs on the device at a time by default, and
everything else waits behind it. A caller blocked on a request has no way to
tell a queue from a hang, and the connection it is holding open is a resource
the service cannot reclaim.

What is given up is real and this record states it rather than leaving it to be
discovered. There is no shape of client that can call this API with a single
blocking request. The simplest possible integration, a script that sends a
photograph and writes the answer to a file, is two calls and a loop. That cost
is paid by every integration, including the ones for which the work would have
finished inside a request timeout.

The mitigation is not a synchronous path added later. It is that creating a job
answers with everything a caller needs to wait well: the identifier, and the
queue position or a plain statement that a position cannot be given.

## Why polling

The first integration in the plan is a photo library plugin, #58, and what that
surface needs is a bar that finishes. A poll gives it one.

Three things make the poll the cheaper half of the pair here, and none of them
is about the client. It is authorised by the same rule as every other read of a
job, which is #53's per-job rule and not a second one written for a long-lived
connection. It is rate limited by the same lever as every other route, which is
#54's. And it is tested by calling a function twice, rather than by holding a
connection open in a suite that has to stay fast and deterministic.

What is given up is latency. A client learns about a step boundary at its next
poll and not when it happened, so a progress bar moves in the interval the
client chose. For work measured in seconds per step that is a bar that looks
slightly behind, which is a different thing from a bar that does not move.

A stream is not ruled out. Under the compatibility rule below, adding one is a
compatible change: a route that did not exist appears, and no client that never
asked for it can tell. So the argument for a stream is one that can be had again
when there is a client whose need for it is measured rather than anticipated,
and it costs nothing today to leave it out.

## What the version in the path promises

`/api/v1` is a promise that a client written against this surface goes on
working. The major number is the whole of it. A minor number in a path would
suggest a caller has something to pin below the major, and it does not: a
compatible change is one no correct client notices, so there is nothing for the
smaller number to tell anybody.

The release version is a different number answering a different question, and it
is #89's. Nothing in this record says the two move together, because they do
not: a release that changes no promise leaves this number where it is.

## What may change inside a version

Compatible, and shipped in any release under `/api/v1`:

- an endpoint that did not exist
- an optional field on a request
- a field on a response
- a new member of the refusal vocabulary
- a new value of an enumerated field a client does not send, for example an
  operation or an engine identifier that an engine declaration carries

Breaking, and it takes a new major number and a surface served alongside the old
one for as long as the release notes say:

- removing or renaming an endpoint or a field
- making an optional request field required
- narrowing what an existing field accepts
- changing what an existing field means while its name and type stand still
- removing a member of the refusal vocabulary
- changing the shape a refusal is carried in

The first list has a condition attached to it that binds the client rather than
the server, and a client that does not meet it will break on a compatible
change. A field it does not recognise is ignored. A refusal code it does not
recognise is shown as its sentence and treated as unclassified, never as a
success and never as a code the client happens to know. Both are stated here
because a server cannot enforce either, and a rule nobody wrote down is one a
client author has no reason to follow.

## The capability declaration is part of the surface

#21 has the API publish an engine's capability declaration so an integration
builds its interface from what an engine says rather than from what its author
assumed. That declaration reaches a caller, so it is under this promise like
everything else, and the endpoint rule alone answers it wrongly.

The split this record makes is between the declaration's shape and its content.
The shape is under the version: a field is not removed, renamed or narrowed
inside `/api/v1`. The content is not, and it cannot be, because it is whatever
the engines an operator has installed happen to declare. An engine gaining an
operation, an engine appearing, an engine leaving because the operator removed
its model, are all ordinary and none of them is a version change.

What follows for a client is the rule above, made specific. A form built from a
declaration is built at run time from the declaration the service returned, and
an operation or a field it does not recognise is skipped rather than fatal. A
client that hard-codes the set it saw once has built against a fact about one
operator's machine, and this record does not promise that fact anywhere.

## The refusal shape

Every endpoint refuses in one shape: a machine-readable `reason`, a human
sentence in `message`, and `parameter` naming the one input the refusal is about
or null where it is about none. `src/retusche/api/refusal.py` is the declaration
and `docs/api/openapi.json` is where a client reads it.

Two rules make it worth having. Nothing parses `message`, so the sentence can be
rewritten, translated or made more specific in any release. And the vocabulary is
closed, with every member standing for a refusal that already exists in this
tree, so no code is promised in advance of something that can raise it.

## What was not evaluated

No measurement of any kind was made here, of latency, of poll cost, or of the
overhead a stream would carry. Nothing above rests on one. The arguments are
about what the queue already decided and what the plan's first client needs, and
where this record says a poll is cheaper it means cheaper to build, to authorise
and to test, not measured to be cheaper to run.

Nothing here was tried against a real integration either. The first one is #58,
and it is the first thing that will find out whether a two-step flow is as
tolerable as the paragraph above claims.

## What would reverse it

A client whose need for a stream is measured rather than anticipated does not
reverse this record; it adds a route under the rule above.

What would reverse the asynchronous decision is a shape of work where the wait is
bounded and short by construction, which the device budget and single-lane
admission are the reasons it is not. If those ever stop being true, the argument
above stops holding and this record is where to start reading.
